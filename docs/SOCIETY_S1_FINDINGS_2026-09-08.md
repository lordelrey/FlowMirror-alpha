# S1 社会测度层：跑出来的结果与它对 S2 的判决（2026-09-08）

模块：`flowmirror/analysis/society_metrics.py`（引擎零改动，只读事件日志与 `run_meta.json`）
命令：`python -m flowmirror.analysis.society_metrics <run_dir> [<run_dir> ...]`
产物：每个运行目录下的 `analysis/society.json`

S1 的任务不是给论文一个漂亮的统计量，而是**回答 S2 能不能做**：
跨种子的累积优势实验需要一个逐帖的份额向量，而一次 40 人 × 12 日的运行只有
24 笔申购。所以这一轮先把信号数出来，再决定因变量。

---

## 一、最值得写进论文的一个数：注意力在点击这一步塌缩

| 运行 | 层 | Gini | HHI | 头名份额 | 非零帖子 |
|---|---|---|---|---|---|
| `viewer_two_arm`（40 人 / T·TV） | 曝光 | 0.551 | 0.022 | 0.039 | 94 / 96 |
| | **点击** | **0.936** | 0.175 | 0.321 | **12 / 96** |
| | 评论 | 0.662 | 0.029 | 0.063 | 52 / 96 |
| | 申购 | 0.911 | 0.111 | 0.208 | 12 / 96 |
| `viewer_three_arm_images`（60 人 / T·TC·TV） | 曝光 | 0.533 | 0.021 | 0.037 | 96 / 96 |
| | **点击** | **0.920** | 0.121 | 0.205 | **13 / 96** |
| | 评论 | 0.648 | 0.027 | 0.045 | 55 / 96 |
| | 申购 | 0.908 | 0.102 | 0.152 | 12 / 96 |

**推荐器把曝光铺得很平**——96 条帖子几乎每条都被人看到，曝光 Gini 只有 0.53–0.55。
**塌缩发生在推荐器之后**：进到点击这一步，Gini 跳到 0.92–0.94，96 条帖子里只有
12–13 条被点过。这个跳跃不是平台造成的，是 agent 的集体选择造成的。

这正是业主要的那件事——个体互动最终形成宏观结构，而且**今天就能测，不用改引擎**。
它也回答了"散户资金太小、影响不了市场"的顾虑：散户在价格上没有力量，
但他们对**可见性**的集体处置极不平均，而可见性是营销的全部标的。

### 这不是漏斗的算术，是真的集中——用零模型验过

上面那张表有一个显而易见的反驳：点击总共才 56 次，摊到 96 条帖子上不可能不尖。
所以我把同一个配置放大到 **400 人 × 12 日**（mock，35 秒）再看一次，
并拿一个**均匀随机零模型**对照——同样的点击总数，随机撒到 96 条帖子上会怎样：

| 400 人 × 12 日 | 有信号的帖子 | Gini |
|---|---|---|
| 曝光（28,800 次） | 92 / 96 | 0.528 |
| **点击（501 次），实测** | **17 / 96** | **0.900** |
| 点击，**均匀随机零模型**（同样 501 次） | **95.5 / 96** | **0.242** |
| **申购（325 次），实测** | **17 / 96** | **0.880** |
| 申购，均匀随机零模型（同样 325 次） | 92.7 / 96 | 0.300 |

501 次点击摊到 96 条帖子上，平均每条 5.2 次；**随机分配的话几乎每条都会被点到**
（零模型 95.5 条）。实测只有 17 条。**算术解释就此排除**：
集中不是因为点击太少，是因为 agent 一起挑同一批帖子。

而且它**不随规模消散**：人数放大近 10 倍、点击放大近 10 倍，
有点击的帖子只从 11–13 条变成 17 条，Gini 从 0.94 只降到 0.90。
所以论文可以直接说集中度，不必退守成"相邻两级的落差"。

## 二、S2 的因变量：只有评论够用

| 候选因变量 | `viewer_two_arm` | `viewer_three_arm_images` | `viewer_null` |
|---|---|---|---|
| 点击 | 12 / 96 | 13 / 96 | 10 / 96 |
| **评论** | **52 / 96** | **55 / 96** | **55 / 96** |
| 申购 | 12 / 96 | 12 / 96 | 10 / 96 |

点击与申购的非零帖子数在 10–13 之间。在 12 个非零点上算份额 Gini，
再拿它做跨种子的方差与名次相关——那是噪声，不是结果。
**评论是唯一有一半以上帖子承载信号的量**，S2 的主因变量应当是逐帖评论份额。

若之后仍想用申购做因变量，只有两条路：把运行规模显著放大，
或者按方案 B-1 加"逐帖点赞/收藏事件行"（引擎改动）。**S1 的结论是：先不加。**

## 三、`cross_run` 发现的一个会毁掉 S2 的陷阱

跨种子比较需要"同一批帖子在不同世界里的命运"。实测：

```
同配置换种子（demo_three_arm --mock --agents 42 --days 12，seed 2027 vs 3031）
  每次运行的帖子数        96 / 96
  帖子 id 集合是否相同    True
  发帖序列是否相同        False
  第一个不同处            p="00000"：seed 2027 是 intent=I1, fund=None
                                     seed 3031 是 intent=I2, fund=001701
```

**帖子 id 是 `00000`…`00095` 的顺序槽位号，每次运行都一样；槽位背后的创意随种子变。**
所以"id 集合相同"这个判据会通过，然后把 A 世界的 0 号帖和 B 世界的 0 号帖当成同一个东西比——
它们是两条不同的营销笔记。跨种子的路径依赖结论会因此完全无意义。

这个坑此前没暴露，是因为三个 `viewer_*` 样本都是 `seed=2027`，只有人数和臂不同，
发帖序列逐条相同——那个巧合掩盖了它。模块现在同时比对逐帖身份
（`org` / `intent` / `ig` / `fund`），不一致就返回 `None` 并点名第一个冲突的 id。

**这直接改写了 S2 的做法**：跨世界的"同一首歌"必须锚在内容池的 `note_id` 上，
而不是引擎的 post id。`note_id` 目前只在展示包的 `posts.json` 里，不在事件日志里。
所以 S2 开工前需要业主拍一个板（见第六节）。

## 四、羊群：LLM 运行上这个指标没有信息量

LSV 按 (基金, 日) 分格，方向取该人当日在该基金上的首笔交易，
`AF` 对 `X ~ Binomial(N, p̄)` 精确求和（不是近似，也不是旧 `gates.py:118` 留的 TODO）。

| 运行 | 赎回数 | 合格格子（阈值 2 / 3 / 5） | 平均 LSV |
|---|---|---|---|
| `viewer_two_arm` | 0 | 6 / 3 / 0 | NA |
| `viewer_three_arm_images` | 0 | 10 / 3 / 0 | NA |
| `viewer_null`（规则型） | 32 | 10 / 7 / 4 | 0.093 |

**两次 LLM 运行 12 天里一笔赎回都没有。** 于是每个格子只有买方，`p ≡ 1`，
指标退化。模块如实报 `None` 并在 `note` 里说明原因，而不是印一个 0 让人误读成"无羊群"。
只有规则型运行有双向交易，算出 0.093。

这里踩到过一个陷阱，值得记下来：基准 `p̄` 一开始按"当日**合格**格子"算
（发卡时我写错了规格）。合格格子恰好清一色买方，于是基准等于子集自己的均值，
`|p − p̄|` 恒为 0，`AF(N, 1)` 也恒为 0——**指标在数据最一边倒的时候恰好报"无羊群"**。
改回 LSV (1992) 的全市场基准（当日**全部**格子）之后，同样这 4 个格子给出
`+0.0000 / +0.0128 / +0.1578 / +0.2033`，均值 0.093。筛选只决定哪些格子进均值，
不决定基准是多少。

## 四点五、追下去发现的一个真缺陷：mock 从来不会卖

第四节说"LLM 运行 12 天零赎回"，我没有停在那里，而是把盘上**全部 52 个运行**数了一遍：

```
agent_policy = llm 的运行：43 个，赎回数 0 / 0 / 0 …… 全是 0，一个例外都没有
agent_policy = null 的运行：赎回很多（viewer_null 41 买 / 32 卖）
```

43 个里一个例外都没有，就不是样本量问题。用 `--dump-prompt` 抓一张真实提示对照：

```
你的风险测评等级：C4。
账户可投闲钱：55,668 元。
003142 / 003142 / R3 / 73,845.06份 × 净值0.9600 / 浮动盈亏 -4.1%   ← 持仓确实渲染出来了
【00021】机构：汇添富基金 ｜ 热度：0.0 赞
```

持仓渲染得好好的，但 `runtime.py` 的 `_held_codes` 找的是 `held:` / `held：` /
以 `持仓` 开头的行——**这三个标记提示一个都不生成**。实测 `_held_codes(prompt) -> []`。
于是 `_trade` 里这一支从项目开始就是死代码，一次都没执行过：

```python
        if held and roll < 0.35:
            return {"action": "redeem", ...}
```

这和上一轮修掉的「MockLLM 把 TC 臂决策提示误判成反思提示」是**同一类缺陷**：
mock 拿一个提示里根本不存在的标记去解析提示。

**已修**：判据改为同一行里同时含 `份 × 净值` 与 `浮动盈亏`（生成器保证、别处不出现），
旧的三个标记保留不删。**没有动 `prompt.py`**——改提示会改掉每次运行的 `prompt_sha`，
那是要预注册的引擎变更。修后同配置同种子重跑：赎回从 0 变成 48，
`--replay-check` 仍逐字节相同，`pytest` 366 项仍全过。

**血止住了，但比例现在偏到了另一边**，这条要业主定：

| | 申购 | 赎回 | 赎回/申购 |
|---|---|---|---|
| 真实面板（2019+，22,962 个基金季） | 51,916 亿份 | 44,915 亿份 | **0.87** |
| 沙盒 mock，修前（42 人 × 12 日） | 38 | 0 | 0.00 |
| 沙盒 mock，修后（42 人 × 12 日） | 14 | 48 | 3.43 |
| 沙盒 mock，修后（**400 人 × 12 日**） | 325 | 371 | **1.14** |

**这个比例本身是规模的函数，别在小规模上下结论。** 42 人时是 3.43，
放大到 400 人就落到 1.14——已经很接近真实参照的 0.87。
原因不难想：小规模下能落地的申购很少（多数买单被适当性门挡掉），
而只要有人持仓，赎回就按日概率稳定发生；人一多，申购这边才起得来。

所以「mock 卖得太多」多半也是小样本假象。`_trade` 那两个阈值
（买 `roll < 0.25`、卖 `roll < 0.35`）**大概不需要动**——
真要调也应该在 400 人规模上校准，不是在 42 人上。

**一条让人松口气的核对**：盘上 17,014 条 LLM 缓存的 `provenance.raw` 全部是 mock 的
固定文案（`_MOCK_REASONS` 里的句子），**没有任何一次真实 provider 调用**。
也就是说这个缺陷没有污染任何论文结果——它在真模型跑之前就被修掉了。

## 四点七、S1b 需要的不是更好的代码，是更大的运行

下一步 S1b 要把六项风格化事实的**模拟侧**估出来。在动手写之前先量了一次，
结论是当前规模根本估不动：

| | 42 人 × 12 日 | **400 人 × 12 日** | 真实面板 |
|---|---|---|---|
| 交易笔数 | 62 | 702 | — |
| 涉及基金 | 39 | 154 | 1,272 |
| (基金, 日) 格子 | 57 | 341 | 19,384 基金季 |
| 双边格子（LSV 要） | 1 | 14 | — |
| ≥5 人的格子 | 0 | 27 | — |
| F1 回归的剩余自由度 | **7** | **176** | — |

F1（流量—业绩敏感性）要带基金与日两套固定效应。42 人时 57 个观测配 50 个固定效应参数，
**剩 7 个自由度，估不出来**。放到 400 人就有 176 个，可以估了。
LSV 同理：42 人时合格格子 0 个，400 人时 27 个，平均 LSV 0.283。

**代价很低**：400 人 × 12 日的 mock 跑完只要 **35 秒**（5,600 次调用）。
真模型跑当然贵得多，但 S1b 的估计器**开发与自检**完全可以在 mock 的 400 人规模上做。

所以 S1b 的正确起手不是"移植 `stylized_facts.py`"，而是先把标准运行规模从 40 人抬到 400 人。
这一条不需要业主拍板——它是运行参数，不是机制变更。

**但有一个量不随规模变好**：有点击/有申购的帖子数从 12–13 只涨到 17（见第一节）。
所以第二节的结论不变：**S2 的因变量仍然只能是评论份额**（400 人时 82 / 96 条帖子有评论）。

## 五、立场熵：目前的沙盒没有极化

| 运行 | 总体熵 | 归一 | 分臂归一 |
|---|---|---|---|
| `viewer_two_arm` | 1.583 bit | 0.999 | T 0.987 / TV 0.997 |
| `viewer_three_arm_images` | 1.580 bit | 0.997 | T 0.994 / TC 0.982 / TV 0.989 |
| `viewer_null` | 1.570 bit | 0.991 | — |

三分立场的上限是 `log2(3) = 1.585 bit`。实测归一熵 0.98–0.999，**几乎顶格**：
看多、看空、观望三分天下，没有任何趋同或极化，臂之间也看不出差别。

这是一个诚实的零结果，而且有用：它说明**当前的社交通道没有产生意见动力学**。
若论文想讲极化，得先有一个机制让它发生（气候权重、可见的同侪立场），
现在的配置下写"羊群"或"极化"都没有证据支撑。

## 六、要业主拍板的两件事

### 6.1 S2 的跨世界身份锚点

S2（MusicLab 复现）需要"同一首歌在不同平行世界里的命运"。三个选项：

1. **把 `note_id` 加进 `post` 事件行**（一个字段的引擎改动）。最直接，
   跨种子身份从此可用。要按引擎变更预注册，会改 `post` 行的哈希。
2. **让创意分配不随种子变**（把发帖抽样挪到独立派生流）。改动更大，
   而且会改变现有全部运行的日志。
3. **不跨种子做 MusicLab，改为同种子跨"社交开/关"做**。零改动，
   但失去 MusicLab 最核心的"平行世界"设计，只剩集中度对比。

我的判断是 1：改动最小、语义最干净，而且 `note_id` 本来就已经在展示包里流通。
但它是引擎变更，按规矩要业主点头。

### 6.2 标准运行规模要不要从 40 人抬到 400 人

见第四点七。这**不是**机制变更，是运行参数，严格说不需要拍板；
但它决定 S1b 能不能开工，而且会改变所有演示与开发运行的耗时（mock 35 秒，真模型另算），
所以还是说一声。我的建议是：**S1b 的估计器在 400 人 mock 上开发与自检**，
真模型的规模另行决定。

（原本这一格是"mock 赎回倾向该调到多少"。量过之后发现那个 3.43 是小样本假象，
400 人时是 1.14、真实参照 0.87，**不用改阈值**。见第四点五。）

## 七、这一轮没做、也不打算顺手做的

- 不做幂律拟合、不估尾指数。96 条帖子、143 条评论，做不了。
  `comment_burst` 只报完整的降序计数向量与集中度，`note` 里写明了这一点。
- 不为分析层加任何门禁。样本不足就写 `None` 加 `note`，退出码始终 0。
- 不动 `data/` 下任何文件，不读展示包，只吃运行目录与 `run_meta.json`。
